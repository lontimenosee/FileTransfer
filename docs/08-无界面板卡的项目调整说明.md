# 无界面板卡的项目调整说明

## 1. 为什么要调整原来的思路

一开始项目按照最容易调试的方式，拆成了：

- 一个图形化发送端
- 一个图形化接收端

这种方式适合 Windows 本机调试，但现在你已经明确了一个重要条件：

`i.MX6U` 没有图形界面。

这意味着板端不能依赖按钮、窗口和文件选择框来操作，所以项目需要调整为更符合实际部署的结构。

## 2. 调整后的推荐结构

推荐把整个系统理解成两个角色：

### Windows 主机

Windows 是主要操作端，负责：

- 输入 IP 和端口
- 选择要发送的文件
- 选择接收文件的保存目录
- 显示日志
- 显示进度条
- 做本机自检
- 作为答辩演示界面

### i.MX6U 板端

板端没有图形界面，所以更适合做成：

- 命令行程序
- 后台服务程序

板端只需要通过命令行参数或配置文件完成：

- 连接主机
- 监听端口
- 发送文件
- 接收文件

## 3. 为什么 Windows 端要能“收”和“发”

因为你后面的真实使用场景不是单向的。

你可能会遇到两种情况：

1. Windows 把文件发给板卡
2. 板卡把日志、结果文件或数据文件发回 Windows

所以 Windows 端不能只做发送工具，也不能只做接收工具，而是应该逐步演化为一个“主控端”。

## 4. 为什么仍然保留当前 client/server 工程

虽然最终架构会升级，但现在保留这两个工程是有意义的。

原因是：

1. 它们适合先把 TCP 协议跑通
2. 它们适合在 Windows 本机做回环测试
3. 它们能帮助你先验证文件头、文件内容和进度显示逻辑
4. 后面重构成主机端/板端时，可以复用很多共享代码

所以当前工程不是白做，而是“第一阶段调试版”。

## 5. 后面建议演化成什么结构

后续更适合的目录结构可以是：

```text
FileTransfer/
|-- host_app/        Windows 图形主机
|-- board_cli/       i.MX6U 命令行程序
|-- shared/          协议与公共代码
|-- docs/
`-- tools/
```

其中：

- `host_app/` 用来提供图形化控制界面
- `board_cli/` 用来跑在无界面的开发板上
- `shared/` 保持两边的协议一致

## 6. 为什么这种结构更适合课程设计

这种结构既符合真实场景，也容易写进报告。

你在报告里可以这样解释：

> 考虑到 i.MX6U 开发板缺少图形界面，系统采用“Windows 图形主机 + 板端命令行节点”的分层架构。Windows 端负责人机交互、传输控制与结果展示，板端负责网络连接和文件收发执行。该结构既满足嵌入式平台实际使用条件，也便于系统调试和课程答辩演示。
