## 2. 问题一：终端里找不到 `qmake`

### 现象

在终端中执行：

```powershell
qmake -v
```

会提示找不到 `qmake`。

### 原因

这不是 Qt 没安装，而是当前终端没有拿到 Qt 的命令行环境。

也就是说：

- Qt Creator 里可能能用
- 但 PowerShell 里不一定直接能用

### 解决方法

把 Qt 和 MinGW 的 `bin` 目录临时加入 `PATH`。

本项目实际使用的是：

```text
D:\Linux\QTcreater\App\6.11.0\mingw_64\bin
D:\Linux\QTcreater\App\Tools\mingw1310_64\bin
```

临时命令示例：

```powershell
$env:Path = 'D:\Linux\QTcreater\App\6.11.0\mingw_64\bin;D:\Linux\QTcreater\App\Tools\mingw1310_64\bin;' + $env:Path
qmake -v
mingw32-make -v
```

### 结果

这样之后，终端就可以直接编译 Qt 工程了。

## 3. 问题二：编译成功，但运行 exe 时提示缺少 dll

### 现象

程序已经编译出了 `.exe`，但双击运行时提示缺少若干 `dll`。

### 原因

Qt 工程“编译成功”并不等于“发布完成”。

编译只会生成你的程序本体，但不会自动把 Qt 运行时库复制到 exe 所在目录。

### 解决方法

使用 `windeployqt` 给程序补齐运行依赖。

例如：

```powershell
windeployqt D:\Linux\QTcreater\Prj\FileTransfer\build-host\release\FileTransferHost.exe
```

### 结果

执行后，Qt 的核心 dll 和平台插件会被部署到可执行文件附近，程序才能在资源管理器里正常运行。

## 4. 问题三：本机环回能通过，但跨端传输大一点文件就不稳定

### 现象

- 本机 `127.0.0.1` 回环测试正常
- 跨设备传输时，小文件可能成功
- 稍大一点的文件开始不稳定

### 原因

根本原因是对 `TCP` 的理解不够完整。

TCP 传输的是“字节流”，不是“消息包”。这意味着：

- 协议头可能被拆开多次到达
- 元数据和文件内容可能粘在一起到达
- 不能假设一次 `readyRead` 就正好收到完整头部

### 解决方法

把接收端改成“缓冲区 + 状态机”的解析方式：

1. 先把收到的字节放进缓冲区
2. 判断是否够解析固定协议头
3. 判断是否够解析元数据
4. 再按剩余长度写入文件

### 结果

这样后，接收端对 TCP 分包和粘包更稳，不再只适合本机演示。

## 5. 问题四：发送端显示发送成功，但接收目录里找不到文件

### 现象

- 发送端提示成功
- 但接收目录里看不到新文件

### 原因

这个问题曾经由多种原因叠加造成：

1. 发送端的“成功”过早定义为“本地写完发送缓冲区”
2. 不代表接收端真的保存成功
3. 接收端在连接关闭时，可能还有尾部数据没来得及处理
4. 同名文件可能被覆盖或看起来不明显

### 解决方法

我们做了三类修复：

1. 增加接收完成回执 `ACK`
2. 发送端只有在收到接收端确认后，才算真正发送成功
3. 接收端增加最终保存路径日志
4. 同名文件自动重命名，而不是静默覆盖

### 结果

现在“发送成功”的含义更严格，也更适合真实调试和答辩展示。

## 6. 问题五：本地大文件可以发，但第二次继续发送会卡住

### 现象

- 第一个文件发送成功
- 第二次选择另一个文件再发，会卡住
- 手动断开重连后又恢复正常

### 原因

最初的设计试图在“同一条 TCP 连接”上连续发送多份文件，但这会让状态机复杂很多。

特别是：

- 第一份文件接收结束后
- 接收端未必已经完美回到“等待下一份文件头”的状态
- 于是第二份文件的头部虽然发出来了，但接收端不一定开始下一轮解析

### 解决方法

为了优先保证稳定性，主机版后续改成了：

**一份文件对应一次独立连接会话**

具体做法是：

1. 一份文件传完
2. 接收端保存成功并返回确认
3. 本次连接自动结束
4. 下一次点击发送时，程序自动重新连接并发送

### 结果

这样虽然连接复用能力弱一些，但逻辑清晰、稳定性更高，也更适合课程设计阶段。

### 进一步经验

开发过程中还尝试过“未连接时自动连接并立即发送”的方案，但这会让发送状态、文件句柄生命周期和连接状态机耦合得更紧，实际调试中反而更容易出现问题。

因此最终选择回退到更稳妥的方式：

1. 用户先建立连接
2. 再点击发送
3. 单个文件发送完成后程序自动断开

这种方案虽然少了一点自动化，但更容易保证稳定，也更容易讲清楚系统行为。

## 7. 问题六：进度条显示不自然

### 现象

有时接收完成后，进度条马上又回到 `0%`，看起来像没有真正完成。

### 原因

接收端在一份文件结束后，状态被复位得太早。

### 解决方法

调整逻辑：

- 文件接收完成后，先保持 `100%`
- 下一份文件真正开始接收时，再回到 `0%`

### 结果

界面观感更稳定，也更符合用户理解。

---

## 8. 问题七：文件其实收到了，但看起来像“没出现”

### 现象

日志显示传输完成，但用户在目录里看不到明显变化。

### 原因

这通常是下面两类情况之一：

1. 文件保存到了你没有注意到的目录
2. 文件名和原来重复，被覆盖或者难以区分

### 解决方法

1. 在日志中打印完整保存路径
2. 对同名文件自动重命名，例如：
   - `demo.txt`
   - `demo_1.txt`
   - `demo_2.txt`

### 结果

这样就能明确知道文件到底保存到了哪里。

## 9. 当前阶段的经验总结

从目前的开发过程可以总结出几条很重要的经验：

1. 先在 Windows 本机做回环自检，再去连板卡
2. TCP 程序不要假设“一次就能收完整”
3. “发送成功”必须和“接收端保存成功”区分开
4. 对课程设计来说，优先保证稳定，再追求复杂功能
5. 界面日志一定要足够详细，否则很难排查问题

## 10. 后续还可能继续遇到的问题

后面如果继续做 `i.MX6U` 版本，还可能遇到这些问题：

1. 开发板与 PC 不在同一网段
2. 开发板防火墙或权限问题
3. 板端路径权限不足，导致不能保存文件
4. 交叉编译版本不匹配
5. Qt 网络模块在板端缺少依赖

这些问题属于下一阶段的“平台适配问题”，和当前 Windows 端逻辑问题是两类不同的问题。
