# Qt 工程搭建说明

## 1. 为什么选择 `Qt Widgets`

本项目使用 `Qt Widgets`，不是 `Qt Quick`，主要原因如下：

- Widgets 更适合传统工具类桌面程序
- 控件拖拽和布局方式直观
- 对课程设计来说学习成本更低
- 在 Windows 和嵌入式 Linux 上都比较常见

对于文件传输工具，界面重点不是动画，而是：

- 输入参数
- 显示状态
- 输出日志
- 显示进度

这些功能用 Widgets 非常合适。

## 2. 为什么选择 `qmake`

你当前使用的是 `Qt + MinGW`。对于课程设计和零基础同学，`qmake` 比 `CMake` 更容易上手。

原因有三点：

1. Qt Creator 对 `.pro` 支持非常成熟
2. 写法简单，适合快速搭工程
3. 后面给 i.MX6U 重新指定 Qt Kit 时也容易理解

虽然以后工业项目里经常会用 CMake，但当前阶段先用 `qmake` 更稳。

## 3. 客户端和服务端为什么分成两个程序

文件传输本质上是网络通信。最清晰的结构就是：

- 一个程序负责发送
- 一个程序负责接收

这样在调试时非常方便：

- 服务端先启动并监听端口
- 客户端输入 IP 和端口后连接
- 选择文件发送
- 服务端保存文件并显示日志

如果一开始就做成“一个程序同时兼任所有角色”，虽然也能做，但对零基础同学来说更绕。

## 4. 这个工程是怎么传文件的

目前采用的是一个非常适合教学的协议：

1. 客户端先发送协议头
2. 协议头中包含：
   - 魔数
   - 协议版本
   - 文件信息区长度
3. 文件信息区中包含：
   - 文件名
   - 文件大小
4. 然后继续发送文件内容
5. 服务端按顺序解析并写入磁盘

这个方案的优点是：

- 比直接裸发字节流更清晰
- 便于以后加更多字段
- 更容易在报告里讲清楚“关键算法设计”

## 5. 为什么现在还没有做分块和断点续传

不是不能做，而是故意分阶段。

当前第一版先把这些最基础的问题解决：

- TCP 通信是否连通
- 文件头能否正确解析
- 文件内容能否完整写入
- 进度条和日志是否工作正常

当这一版稳定后，再继续加：

- 自定义分块编号
- 分块确认应答
- 断点偏移量记录
- 文件夹遍历和打包

这样的开发顺序是合理的，也更像真实项目。
