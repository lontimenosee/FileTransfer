## 2. 为什么要这样分目录

很多初学者会把所有 `.cpp` 和 `.h` 都放在一个目录下，短期看似方便，但项目稍微变大就会变乱。

本项目这样拆分，是因为：

- `board_cli/` 放板卡端独立命令行程序
- `host_app/` 放统一的 Windows 主机程序
- `client/` 只放发送端程序
- `server/` 只放接收端程序
- `shared/` 放两边都要用到的公共代码
- `tools/` 放校验和辅助脚本
- `docs/` 放设计说明、构建说明、实验记录

这样做的优势很明显：

1. 代码职责清楚
2. 既能保留第一阶段调试程序，也能新增更接近最终形态的主机程序
3. 板卡端和 Windows 端职责更清晰
4. 后续扩展时不容易混乱
5. 提交到 GitHub 后，老师和同学都更容易看懂
6. 写课程报告时，也更容易解释你的工程设计思想

## 3. 为什么根目录使用 `FileTransfer.pro`

根目录的 `FileTransfer.pro` 采用的是 `subdirs` 工程模式。它不直接编译某一个程序，而是统一管理多个子工程。

这样做的作用是：

- 一次打开整个项目
- 可以同时管理客户端和服务端
- 便于以后增加新的子模块

比如以后你想加：

- `tools/`：测试工具
- `sharedlib/`：独立公共库
- `tests/`：单元测试

都可以继续挂到根工程下面。

## 4. 为什么 `shared/` 使用 `common.pri`

`common.pri` 的作用是把公共源码文件集中列出来，然后在 `client.pro` 和 `server.pro` 中直接 `include(...)`。

这么做对于初学者有两个好处：

1. 比单独建立静态库更简单
2. 不容易在不同平台下遇到库链接问题

也就是说，我们现在是在“保留模块化思路”的前提下，选择“更容易成功”的实现方式。

## 5. 为什么要有 `README.md` 和 `.gitignore`

这是 GitHub 项目的基本规范。

`README.md` 用来说明：

- 项目做什么
- 当前实现到哪一步
- 怎么编译运行
- 后续准备做什么

`.gitignore` 用来忽略不应该上传的文件，例如：

- Qt Creator 自动生成的用户配置
- 编译中间文件
- 可执行文件

这样仓库会更干净，老师打开也更专业。
