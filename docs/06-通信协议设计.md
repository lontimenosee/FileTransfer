# 通信协议设计

## 1. 为什么要自己定义应用层协议

虽然 TCP 可以帮我们可靠地传输字节流，但 TCP 并不知道：

- 什么时候开始传一个文件
- 文件名是什么
- 文件大小是多少
- 一段字节是“文件头”还是“文件内容”

所以我们需要在 TCP 之上，自己再定义一层简单协议。

## 2. 当前协议格式

当前第一版协议分成两部分：

1. 固定长度协议头
2. 文件元数据区
3. 文件内容区

### 固定长度协议头

固定长度头里有三个字段：

- `magic`：魔数，用来判断是不是我们的协议
- `version`：协议版本，后续升级时有用
- `payloadSize`：后面元数据区的长度

### 文件元数据区

当前元数据区中包含：

- `fileName`
- `fileSize`

### 文件内容区

元数据后面紧跟实际文件内容。

## 3. 为什么要有魔数

魔数可以理解为“暗号”。

如果服务端收到了一个连接，但发来的数据并不是我们定义的文件传输协议，那么服务端就能通过魔数快速发现问题，然后拒绝连接。

这比“盲目按文件去解析”更安全。

## 4. 为什么要有版本号

课程设计第一版可能只有：

- 文件名
- 文件大小

以后你可能还想加入：

- 文件 MD5
- 分块编号
- 总分块数
- 断点续传偏移量

这时协议就会变化。加上版本号后，升级会更容易管理。

## 5. 为什么先传元数据，再传文件内容

服务端在真正写文件之前，必须先知道：

- 该用什么名字保存
- 文件总大小是多少

否则就无法：

- 正确创建输出文件
- 显示接收进度
- 判断传输是否结束

所以先传元数据是很自然的设计。

## 5.1 为什么接收端不能假设“一次就收全”

这是很多初学者最容易忽略的一点。

虽然发送端可能是“先发头，再发内容”，但接收端看到的是 TCP 字节流。实际到达时可能出现：

- 只收到半个协议头
- 收到完整协议头和一部分文件内容
- 协议头、元数据、文件内容一次性都到了

所以一个稳定的接收端通常需要：

1. 先把数据放进接收缓冲区
2. 判断缓冲区里是否已经够解析协议头
3. 再判断是否已经够解析元数据
4. 最后按剩余长度持续写入文件

这也是为什么后续代码里要采用“状态机 + 缓冲区”的接收逻辑。

## 6. 后续如何升级成分块传输

如果后面要做加分项“大文件分块传输”，协议可以继续扩展成：

- `fileId`
- `chunkIndex`
- `chunkCount`
- `chunkSize`
- `chunkData`

这样每次发送一个块，服务端按编号拼接即可。

## 7. 这部分可以怎么写进报告

你在报告里可以这样描述：

> 本系统采用基于 TCP 的自定义应用层协议。发送端首先发送固定协议头，协议头中包含魔数、版本号和元数据长度；随后发送文件元数据，包含文件名和文件大小；最后发送文件内容。接收端按顺序解析协议头、元数据和文件数据，并将文件内容写入本地磁盘。
