## 一、系统总体设计

本次课程设计围绕“基于 Qt 的主机与嵌入式开发板文件传输系统”展开，系统目标是在 Windows 主机与 i.MX6U 嵌入式 Linux 开发板之间建立稳定、可验证、便于演示的单文件传输链路，并在此基础上完成工程搭建、协议设计、界面实现、板卡适配与上板测试。结合实际硬件条件与课程设计要求，系统最终采用“Windows 图形主机 + i.MX6U 命令行节点”的分层结构。其中，Windows 端负责图形化交互、连接控制、文件选择、进度显示、日志输出与结果展示；开发板端由于不具备图形界面，因此采用基于 QtCore 与 QtNetwork 的命令行程序完成监听接收、主动发送和文件保存等核心功能。该结构既符合嵌入式设备的实际运行条件，也便于在课程答辩中清晰展示系统功能、设计思路与调试过程。

在工程组织上，项目以较规范的目录结构进行划分，分别设置 Windows 主机工程、板卡命令行工程、协议与公共功能模块、文档目录与辅助脚本目录，使系统具备较好的可读性与可维护性。Windows 端主机程序 `host_app` 采用 Qt Widgets 实现，作为最终主要展示界面；板卡端 `board_cli` 采用 Qt Console 形式实现，用于 Ubuntu 环境验证与后续 i.MX6U 上板运行；`shared` 目录用于保存协议结构与文件工具函数等可复用逻辑；`docs` 目录则保存系统说明、协议设计、编译运行、问题整理与迁移说明等文档。这样的结构不仅便于开发阶段分模块调试，也使课设报告中的工程说明更具条理性。

## 二、系统功能设计

本系统当前以“单文件稳定传输”为核心目标，重点完成从发送端文件选择、网络连接建立、文件头信息封装、文件内容分块发送、接收端协议解析、文件落盘保存到结果确认返回的完整过程。Windows 主机端支持输入目标 IP 与端口、浏览待发送文件、建立连接并发送文件，同时也支持设置监听端口与接收保存目录，作为接收端保存来自开发板或其他主机发送的文件。开发板端命令行程序支持监听模式与发送模式两种工作状态，在监听模式下可指定端口和保存目录，在发送模式下可指定目标主机地址、端口与文件路径，从而满足“主机发板卡收”和“板卡发主机收”两种主要实验场景。

考虑到课程设计的可操作性与调试难度，系统没有在初版中直接引入断点续传、文件夹传输和多文件任务队列等复杂功能，而是优先确保单文件传输链路的完整性与稳定性。这样处理的原因在于，网络文件传输系统的关键难点并不只在界面设计，而在于协议定义是否清晰、接收逻辑是否正确、跨设备传输是否稳定以及异常情况下的反馈是否准确。先完成单文件稳定传输，既符合课程设计“先完成核心功能，再考虑扩展”的实现思路，也便于后续在此基础上继续升级校验、分块重传和目录传输等附加能力。

## 三、通信协议设计

由于 TCP 本身只负责按顺序、可靠地传输字节流，并不理解“文件名”“文件大小”以及“本次数据从哪里开始到哪里结束”等应用层语义，因此系统在 TCP 之上设计了一套轻量级应用层协议。整个协议由固定长度协议头、文件元数据区与文件内容区三部分组成。固定长度协议头中包含魔数、协议版本号和元数据区长度，其中魔数用于判断当前连接是否使用了本系统定义的文件传输协议，版本号用于后续扩展和兼容，元数据长度则用于指导接收端从字节流中正确切分出元数据部分。文件元数据区包含文件名和文件大小信息，接收端在解析完该部分后即可创建目标文件、显示接收进度并准备写入后续的文件内容数据。文件内容区则保存实际待传输的文件字节序列。

本系统的接收逻辑没有采用“一次 `readyRead` 就假定收到完整报文”的简单方式，而是使用“接收缓冲区 + 状态机解析”的思路逐步处理 TCP 数据流。原因在于，TCP 传输过程中可能出现粘包与拆包现象，应用层读取到的数据既可能只有半个协议头，也可能一次性收到协议头、元数据和部分文件内容，甚至还可能在同一个缓冲区中包含多个阶段的数据。为提高系统稳定性，接收端先将数据追加到缓冲区，再依次判断是否已经满足解析固定头、元数据和文件内容的条件，最后根据剩余长度持续写入文件。该设计使系统在本地回环测试和跨设备真实网络测试中都能保持较好的稳定性。

为了避免发送端仅凭“本地已经写入 socket 缓冲区”就误判为传输成功，系统还设计了接收确认机制。当接收端完整保存文件后，会向发送端返回 ACK 确认；发送端只有在收到 ACK 后，才将本次传输判定为真正成功。该机制有效解决了“发送端提示完成，但接收目录中实际没有文件”或“文件尚未完全落盘就提前显示成功”等问题，使系统的成功定义更符合真实文件传输的工程语义。

## 四、Windows 主机端设计与实现

Windows 主机端是本系统的人机交互核心，采用 Qt Widgets 设计图形界面，并在一个统一窗口中划分为发送区、接收区和日志显示区。发送区主要用于配置目标主机 IP、端口和待发送文件，用户点击连接后可向目标设备发送选定文件；接收区主要用于配置本地监听端口和文件保存目录，启动监听后即可接收来自开发板端或其他主机端发来的文件；日志区则用于输出连接建立、文件开始发送、传输进度、ACK 确认、接收成功、异常断开等关键过程信息，便于调试和答辩演示。

在实现过程中，主机端对网络连接和文件传输过程进行了较为细致的状态控制。发送端在建立连接后首先发送协议头和元数据，再以固定大小的块读取本地文件并持续写入 socket；接收端则根据协议解析结果创建目标文件，按接收进度将内容持续写入磁盘。为了增强使用体验，系统在界面中加入了发送进度条和接收进度条，用于显示当前传输比例；同时保留了日志信息，避免只依赖进度条导致调试信息不足。由于课程设计更强调功能可验证和流程可解释，因此界面没有采用复杂美化，而是优先保持输入项、按钮、状态文字与日志区域的清晰布局，以提高调试效率和答辩可读性。

主机端还承担了系统自检的重要任务。项目开发过程中，首先通过 Windows 本机回环方式完成自检，即程序在本机监听指定端口，同时向 `127.0.0.1` 发起连接并发送文件，从而验证发送逻辑、接收逻辑、协议解析和文件保存链路是否全部正确。在此基础上，再进一步开展 Windows 与 Ubuntu、Windows 与 i.MX6U 板卡之间的跨设备联调。这样的开发顺序有效降低了问题定位难度，使“代码逻辑问题”与“平台适配问题”能够被分开分析和处理。

## 五、板卡端命令行程序设计与实现

考虑到 i.MX6U 开发板无图形界面这一客观条件，系统为板卡端设计了独立的命令行工程 `board_cli`。该程序不依赖 Qt Widgets，仅使用 QtCore 和 QtNetwork 模块实现，因此更适合部署到嵌入式 Linux 环境中运行。程序支持两种基本模式：一是监听模式，即开发板作为接收端监听指定端口并将接收到的文件保存到指定目录；二是发送模式，即开发板作为发送端主动连接到 Windows 主机或 Ubuntu 测试主机，并发送指定路径下的文件。除完整命令行参数模式外，程序还支持交互式输入模式，可逐步提示用户选择发送或接收、输入目标 IP、端口、文件路径和保存路径，降低了零基础使用者的操作门槛。

在板卡端实现中，程序与 Windows 主机端保持一致的协议设计，并在传输流程上同样采用“协议头 + 元数据 + 文件内容 + ACK 确认”的方式完成通信。接收端利用缓冲区与状态机逐步解析数据，避免由于 TCP 粘包、拆包导致大文件或跨设备传输失败；发送端采用分块写入方式持续推送文件内容，并在全部数据写出后等待接收端确认，以此确保传输完成语义准确可靠。为方便在 Windows 与 Ubuntu 环境中先行验证逻辑，命令行程序还对路径输入、路径合法性校验、错误输入重试等细节进行了处理，并在 Ubuntu Qt 5.12.9 与 Windows Qt 6 环境间做了兼容性整理，从而提升了代码的可移植性。

为了适应后续 Ubuntu 迁移与上板测试，项目还专门整理了板卡端的最小迁移包，仅保留命令行程序源码及其必要文件，避免在 Ubuntu 环境中引入 Windows 图形界面相关部分所造成的不必要编译错误。这样不仅降低了跨平台迁移的复杂度，也使课设中“板卡端独立子项目”的结构更加清晰，便于说明系统的分层设计思想。

## 六、系统调试过程与问题分析

本次课程设计的实现过程并非一次完成，而是在多轮测试、回退、修正和平台适配中逐步稳定下来。开发初期，系统主要在 Windows 本机环境下完成界面搭建和基础收发逻辑验证，此阶段重点解决的是文件头封装、文件保存路径生成、传输进度显示与基础日志输出等问题。随着功能逐步完善，开始进行本地回环测试和跨进程测试，随后进入 Windows 与 Ubuntu 间的联调阶段。在这一过程中，项目暴露出多个典型工程问题，例如发送端过早判定传输成功、接收端对 TCP 数据流解析不稳定、第二次连续发送时连接状态未完全复位、大文件传输中接收方未正确落盘等。针对这些问题，系统逐步引入 ACK 确认、接收缓冲区状态机、自动重命名保存策略和更明确的连接生命周期控制，最终使单文件传输逻辑趋于稳定。

在板卡方向的适配过程中，网络环境配置成为另一类关键问题。由于板卡通过网线直连 Windows 主机网口，并依赖主机转发实现外网访问，因此不仅需要给板卡配置静态 IP，还需要正确设置默认网关与 Windows 共享网络环境。测试中曾出现“板卡只能 ping 本地网段、不能访问外网”“修改网关后可以访问公网但不能访问 Ubuntu NAT 网卡”“Ubuntu ping 板卡时出现 Redirect 与重复回包”等现象。通过分析路由表与链路拓扑后可以确认，这些问题本质上属于虚拟机 NAT 地址、Windows 共享网络和板卡实际通信网段之间的路径差异，而不是文件传输程序本身的逻辑错误。最终在明确使用 `192.168.137.x` 实际互通网段并区分 NAT 网卡地址后，Ubuntu、Windows 与板卡之间的联调链路逐步理顺。

此外，在 Ubuntu 迁移过程中还出现了 Qt 版本兼容问题。由于 Ubuntu 环境中使用的是 Qt 5.12.9，而 Windows 端开发环境使用的是较新的 Qt 6，部分流式输出和网络错误信号连接方式在不同版本间存在差异。通过对代码进行兼容性修改，例如替换在旧版本中不稳定的输出写法、兼容不同版本的 `socket error` 信号连接方式等，最终使板卡端命令行工程能够同时适应 Windows 调试和 Ubuntu 编译测试环境。这一过程也说明，在嵌入式 Qt 项目中，程序正确性不仅取决于业务逻辑本身，还与具体工具链、运行时库版本和目标平台环境密切相关。

## 七、系统测试与结果分析

为验证本次课程设计所实现的文件传输系统具备可用性、稳定性与可演示性，系统测试按照“先本机、后跨主机、再面向板卡”的顺序逐步展开。整个测试过程主要分为 Windows 本机环回测试、Windows 与板卡网络联调测试以及 Ubuntu/板卡端命令行收发验证三个层次，其中前两个部分是课程答辩展示中最具代表性的核心内容。

首先进行的是 Windows 本机环回测试。该测试的目的在于排除外部网络环境、开发板配置与交叉编译条件对结果的干扰，仅针对主机端程序本身的发送逻辑、接收逻辑、协议解析、文件保存机制与进度显示机制进行闭环验证。在测试中，统一主机程序首先在本地启动监听功能，设置监听端口和接收目录，然后在同一程序的发送区域中填写回环地址 `127.0.0.1` 与对应端口，选择待发送文件后建立连接并执行发送。若系统设计正确，则发送端应能够完成协议头与文件内容发送，接收端应能够在指定目录内创建目标文件并完成保存，同时在日志区显示连接建立、开始接收、接收完成与确认返回等完整信息。通过该测试可以证明，主机端的核心传输闭环已经成立，程序在不依赖外部设备的情况下能够独立完成一次完整的单文件传输过程。

在整个联调过程中，测试还覆盖了不同大小文件的传输场景。早期测试中，小文件传输可以较快完成，但在连续发送或较大文件传输时曾暴露出状态复位、ACK 时机和接收端落盘时序等问题。经过后续对接收缓冲区状态机、确认机制和连接生命周期的调整后，系统的大文件传输稳定性得到明显提升，单文件传输的完成判据也由“发送端本地写完 socket”修正为“接收端保存成功并返回 ACK 确认”。因此，当前系统的测试结果已经能够较真实地反映文件传输是否真正完成，而不是仅停留在表面上的网络发送成功。

综合测试结果可以看出，本次设计实现的文件传输系统已经具备较完整的课程设计可用性：一方面，Windows 主机端能够通过本机环回测试完成独立自检，证明核心程序逻辑正确；另一方面，Windows 与 i.MX6U 开发板之间已经能够完成基于实际网络环境的双向文件收发，证明该系统能够适配无图形界面的嵌入式 Linux 开发板环境。虽然在网络配置、平台迁移与调试过程中经历了若干问题，但通过逐步分析与修正，系统已经实现了从本地验证到真实设备联调的完整闭环，达到了课程设计的预期目标。

## 八、课程设计总结

本次课程设计以 Qt 为开发框架，围绕 Windows 主机与 i.MX6U 开发板之间的文件传输需求，完成了从工程搭建、协议设计、界面实现、命令行程序开发到跨平台迁移和板卡联调准备的一整套实现过程。与单纯完成一个界面程序相比，本次设计更强调系统整体链路的完整性与工程实现的真实性，即不仅要实现文件的“发送出去”，还要保证接收端能够正确解析协议、稳定保存文件、反馈完成结果，并能够在不同平台和不同网络环境下逐步验证其可用性。通过本次设计，我进一步理解了 TCP 字节流通信与应用层协议设计的关系，掌握了 Qt 网络编程、文件读写、状态机式接收处理、跨版本兼容和嵌入式无界面程序设计等关键内容，也更加直观地体会到嵌入式系统开发中“代码逻辑、平台环境、网络配置、部署方式”之间的耦合关系。
